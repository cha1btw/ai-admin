# Runbook: эксплуатация и инциденты

## Деплой на VPS (первый раз)

1. VPS в ЕС, Docker с Compose, домен с A-записью на сервер.
2. `git clone`, затем `cp .env.example .env` и заполните: `POSTGRES_PASSWORD`, `DOMAIN`, `PUBLIC_BASE_URL=https://<домен>`, `ENCRYPTION_KEY`, ключи модели, ботов и Meta. `ENV=prod`.
3. Ключ Google (если нужен) положите в `secrets/google.json`, в `.env`: `GOOGLE_SERVICE_ACCOUNT_FILE=secrets/google.json`.
4. Короткая команда (Compose берёт переменные только из явно указанного `.env`):
   `alias dc='docker compose -f deploy/docker-compose.prod.yml --env-file .env'`.
   Запуск: `dc up -d --build` (миграции применяет сервис `migrate`).
5. Проверка: `curl https://<домен>/health` возвращает `{"status":"ok","db":true}`.
6. Вебхуки Telegram: `dc run --rm api python -m app.cli telegram set-webhooks`.
7. Демо-студия: `dc run --rm api python -m app.cli tenant load studios/demo_studio.json --demo`.
8. Бэкап: cron `0 3 * * * /path/to/repo/deploy/backup.sh` и `RCLONE_REMOTE` для копии вне сервера. Раз в месяц: `deploy/restore.sh <файл>`.
9. Внешняя проверка доступности на `https://<домен>/health` (любой бесплатный uptime-монитор).

## Обновление

`git pull && dc up -d --build`. Входящие события лежат в базе, поэтому за время перезапуска ничего не теряется: воркер обработает очередь после старта.

## Адмінка и лендинг

- Вход: `/admin` в Owner Bot (только `ADMIN_TELEGRAM_IDS`), ссылка одноразовая и живёт 10 минут; сессия `ADMIN_SESSION_HOURS` (12 ч). Нужен `PUBLIC_BASE_URL`.
- Лендинг на Vercel: в блоке `CONFIG` в `landing/index.html` указать `apiBase` (`https://<домен>`), `demoBot`, `contact`, цены. В `.env` сервера: `LANDING_ORIGIN=https://<адрес лендинга>`, иначе браузер не пропустит заявку.
- Заявки с лендинга приходят основателям в Telegram (через воркер) и видны в адмінке «Заявки» со статусами.
- Утром в 09:00 по Киеву основателям приходит сводка по всем студиям; стоимость токенов считается, если заданы `LLM_PRICE_INPUT_PER_M` и `LLM_PRICE_OUTPUT_PER_M` (цены модели за 1M токенов из прайса провайдера).

## Где смотреть

- Логи: `dc logs -f worker api` (JSON, без текста сообщений и телефонов).
- Состояние: `/health` у основателей в Owner Bot (очередь, ошибки, диалоги в ожидании).
- Студии: `/tenants`; статистика студии: `tenant stats <slug>`.

## Инциденты

| Что случилось | Что делать |
|---|---|
| Бот назвал неверную цену | Пауза студии в адмінке «Огляд» (или `/pause_all`), исправить данные в адмінке (или откатить версию в «Історія»), прогнать «Автоперевірку», проверить валидатор (`app/brain/guardrails.py`), добавить eval-кейс, сообщить мастеру; что делать с клиенткой, решает мастер |
| Мастер прислал `/change` | Текст в адмінку «AI-оновлення», проверить разницу, сохранить, ответить мастеру, что обновили |
| Двойная запись | Остановить запись у студии; найти обе записи и действия по `audit_log`; база не даёт пересечься записям одного мастера, значит причина вне её (ручное событие в Google, запись мимо бота) — добавить тест на сценарий |
| Утечка или подозрение | `/pause_all`, сменить ключи (бот, модель, Meta, `ENCRYPTION_KEY` с перешифровкой токенов), оценить масштаб по логам, уведомить студии |
| Модель недоступна | Бот уже отвечает шаблоном и передаёт мастеру (алерт «Модель недоступна»). При долгом сбое сменить `LLM_MODEL` или провайдера и перезапустить воркер |
| Не обновился токен Instagram | Алерт «Не вдалося оновити токен». Отправить студии новую ссылку: `instagram link <slug>` |
| Очередь растёт (`/health`) | Логи воркера; события с ошибкой повторяются 5 раз с паузой и затем помечаются `failed` с алертом |
| Google Календарь недоступен | Модель получает `calendar_unavailable` и передаёт диалог мастеру; проверить доступ сервисного аккаунта к календарю |
| Клиентка просит удалить данные | Основателям приходит сообщение с готовой командой `/forget <client_id>`; выполнить после ответа мастера клиентке |

## Ключи и секреты

Только в `.env` и `secrets/` на сервере. В git — `.env.example`. Токены Instagram в базе зашифрованы `ENCRYPTION_KEY`; при его смене нужно заново подключить Instagram студий.
